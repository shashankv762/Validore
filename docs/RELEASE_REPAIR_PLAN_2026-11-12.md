# Public release repair plan — 12 November 2026

This plan was written after read-only code review and baseline verification, before application code changes. Four independent reviewers used GPT-6.1 Sol: authentication/data, jobs/accounting, CI/Render, and dashboard/exports. The workspace started clean at `322c5391c2d62b7adcbbfe9257e46700c07fad6c`.

## Architecture and verified baseline

Next.js 16.4.3 serves the pages and API routes. Supabase Auth establishes identity; the server uses Drizzle and PostgreSQL for private application records. Redis enforces shared abuse and provider limits. Inngest coordinates validation and credit maintenance. The validation coordinator runs three specialists for Lite and nine for Full reports. Stripe subscriptions and optional credit purchases use signed webhooks and transactional accounting. Planning modules save results in PostgreSQL; PDF, Word, PowerPoint and portfolio exports load owner-scoped records. The marketing site in `static webpage/public` is independent of the Render application.

The installed Next.js guides for standalone output, environment variables, route handlers, Proxy and Vitest were read. Baseline lint, generated route types/TypeScript, standalone production build and production smoke passed. The test suite passed 567 tests; eight external-PostgreSQL tests were skipped because no dedicated test database was configured. Release-file verification passed as the normal Windows user. These checks do not establish hosted integration behavior.

GitHub `main` matches the local commit. The current tree contains no GitHub Actions workflow; all four historical CI runs were successful. The existing Render Free service is `validore` at `https://validore.onrender.com`, attached to this repository's `main` branch with manual deployment. Its saved build command runs compatibility validation, local CI, an audit and the standalone build; its start command runs the standalone server with a 256 MB V8 heap. Existing services and secrets will be retained.

## Repair sequence

1. **Authentication and private reports.** Make report sharing require authenticated ownership in both content and metadata, validate share UUIDs before SQL, and protect private responses from caching. Enforce consent and registration controls when Google OAuth introduces a new application account, including entry from the sign-in page. Preserve existing account sign-in and password recovery. Add regressions for anonymous, foreign-owner, malformed-token and new/existing Google identity cases.
2. **Persistence and accounting.** Normalize bounded AI scores before inserting PostgreSQL integer columns across validation and planning modules. Give credit cycles an explicit start/identity and reconcile subscription periods with lazy resets and refunds; cover 28-, 30- and 31-day periods, duplicate/delayed renewal events and failures spanning a cycle. Use additive, reviewed database changes if necessary. Preserve purchased and earned credit sources.
3. **Dashboard and saved results.** Restore drafts before enabling persistence, offer existing idea selection/reuse so Free users can spend their second included validation, and collect a real crowdfunding description. Add owner-scoped module history/detail retrieval without requiring another generation entitlement. Reopen results after refresh and exhausted run packs. Align pricing's zero-CAC semantics and pitch integrity-note rendering with saved data.
4. **Exports.** Carry the selected simulation, analysis and deck identifiers through toolbars. Select the requested record and module for PowerPoint and portfolio exports. Verify actual document contents with conflicting versions and modules, plus ownership denial.
5. **CI and release configuration.** Restore GitHub Actions on push, pull request and manual invocation. Run a reproducible Node 24 install, release-file checks, lint, types, unit/regression tests, actual PostgreSQL integration tests in an isolated schema, production dependency audit, standalone build, browser-asset smoke and static-site checks. Validate release origins and public-key formats before building, reject private keys, supply deployment revision attribution, and align Docker's public-key/build contract where relevant.
6. **Hosted preparation and deployment.** Inspect the existing Render deployment/settings and actual database schema/grants without printing secrets or customer content. Back up the target and verify any required additive SQL on an isolated database before application rollout. Preserve external credentials and configured services. Push the reviewed commit, wait for GitHub checks, deploy that exact commit on the existing Render service, and verify revision, assets, auth boundaries, dependencies and a controlled authenticated workflow.
7. **Final review and evidence.** Independently review the final changes, resolve confirmed regressions, record exact checks and deployment evidence, and update current documentation. Report any external configuration that cannot be verified; do not label untested email, payment or provider behavior as passed.

## Verification boundaries

Use synthetic external services for ordinary tests, isolated PostgreSQL for transaction tests, and minimal deliberate hosted calls for release acceptance. Do not run seeds or destructive schema synchronization against existing customer data. Do not disable security controls to make a check pass. Do not replace tests with empty stubs or omit failing gates. Optional integrations should remain honestly unavailable until configured. A successful build or liveness response alone is insufficient evidence of public readiness.
